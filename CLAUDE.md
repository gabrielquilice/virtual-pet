# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A pixel-art desktop pet written in Python 3.12+ with PySide6 (Qt 6), managed with uv. The species are in `src/virtual_pet/pets/` and the README's table. The stack is cross-platform, but the app is built and tested for Linux (KDE Plasma 6 on Wayland, through XWayland); a Windows build is made and tested under Wine, and the user saw it work on several Windows 11 PCs (Windows 10 is untried). The scope is deliberately small: the pet roams on its own, a click makes it sit (another click lets it roam), it can be dragged anywhere but never off the screen, and its right-click menu offers Sit/Walk (the sit and roam texts depend on the species), Pet ("Fazer carinho"), Turn around, Hide, Settings… (name, species and language) and Quit. Hide puts the pet away in the system tray, or, on desktops without one, until the app is opened again. The interface is in English or Brazilian Portuguese, in which the app is called Pet Virtual. It ships as an x86-64 Linux AppImage, built by `appimage/build.py`, and as a Windows zip, built on Linux by `windows/build.py` under Wine. Both run locally, and in `.github/workflows/release.yml` for each pushed `v*` tag, which attaches them to a draft GitHub Release. Run from source on Debian/Ubuntu, Qt's X11 backend needs `libxcb-cursor0`; the AppImage bundles it.

## Commands

```bash
uv sync                      # .venv with runtime and dev dependencies
uv run virtual-pet           # run the app (same as: uv run python -m virtual_pet)
uv run pytest                # full suite on Qt's offscreen platform; fails below 80% coverage
uv run pytest tests/test_behavior.py::test_sitting_pet_stays_where_it_is --no-cov
                             # a single test: --no-cov, otherwise the coverage gate fails the run
uv run ruff check . && uv run ruff format --check .
uv run ty check src/
uv run appimage/build.py     # dist/VirtualPet-<version>-x86_64.AppImage, then its process tests
uv run windows/build.py      # dist/VirtualPet-<version>-windows-x64.zip under Wine, then a start of it
uv version --bump minor      # a release: then commit it as chore(release): X.Y.Z and tag it vX.Y.Z
VIRTUAL_PET_EXECUTABLE=$PWD/dist/VirtualPet-<version>-x86_64.AppImage uv run pytest -m process --no-cov
                             # the process tests against a built AppImage
uv run pyside6-lupdate src/virtual_pet/*.py src/virtual_pet/pets/*.py -locations none -no-obsolete \
    -ts src/virtual_pet/translations/virtual_pet_pt_BR.ts
                             # after changing UI texts: new ones come in unfinished, gone ones go
uv run pyside6-lrelease src/virtual_pet/translations/virtual_pet_pt_BR.ts   # the .qm the app loads
uv run python -c "from virtual_pet.icon import icon_image; icon_image(256).save('docs/icon.png')"
                             # after changing the icon: the README's picture of it
uv run python -c "from virtual_pet.pets import ALL_SPECIES
for s in ALL_SPECIES: s.image(s.portrait).scaled(32 * 6, 27 * 6).save(f'docs/pets/{s.key}.png')"
                             # after changing or adding a pet: the pictures in the README's table
```

Add dependencies with `uv add` or `uv add --group dev`. Dev tools live in `[dependency-groups]`; PyInstaller is in the `build` group.

## Architecture

- **`behavior.py`** is the pet's brain, in plain Python with no Qt.
  - `PetBehavior` is a small state machine. `Activity` is derived from flags in this order: carried, sitting, walking (has a target), standing.
  - Positions are the window's top-left corner. `Area` is the allowed range for that corner: the screen's available geometry minus the window size. Every move is clamped to it, which is how "never off the screen" is enforced.
  - `Gait` (speed, max slope, stroll length, rest between strolls, backward, pulse) comes from the species. `tick()` caps dt at 0.1 s so the pet doesn't teleport after a system sleep. `set_gait()` (a species swap) lets a stroll under way go on, but a gait without `backward` turns the pet to face where it goes.
  - `Gait.backward` is the share of strolls taken facing away from where the pet goes (0 by default). `_start_stroll` draws from `rng` for it only when it is above 0, so no other species' random sequence changes. `turn_around()` flips the facing along with the mirrored stroll, so a backward stroll stays backward.
  - `Gait.pulse` is the seconds per stroke of a pet that moves in surges (None, the default, is a steady pace). The speed swings around the mean and a tick moves the pet by the difference of the exact integral `pulsed_distance()`, so the tick's length doesn't matter. Every stroll lasts whole pulses, so it ends at its slowest and glides to a stop: `_fit_pulses()` picks the number of pulses that brings the mean speed closest to `gait.speed` and sets `stroll_speed`. It works mid-stroll too, and is called when a stroll starts, when `turn_around()` shortens it against a wall, when `set_area()` clamps its target and when `set_gait()` changes the gait. The user's commands (`pet()`, `toggle_sitting()`, `pick_up()`, `turn_around()` against a wall) still stop it at once. `PetWindow` restarts the WALKING animation on the tick the activity changes, which is the one a stroll starts on, so an animation as long as the pulse stays in step with the surges.
  - A throw: `put_down(velocity)` with the cursor's speed at release (the window averages its last `THROW_WINDOW`) at or above `THROW_SPEED` makes the pet fly. While `flying` its activity stays CARRIED (the carried sprite); it glides in a straight line, slowed by `THROW_FRICTION` until it stops (no gravity), and a wall or the screen's edge sends it back (`BOUNCE`); then it goes back to sitting or strolling. `Config.throw_strength` (25 to 225, default 100; anything else in the file falls back to 100) scales its take-off speed and its bounce, set by the "Throw strength" slider in Settings. Grabbing it mid-flight catches it. The window ticks at 33 ms while it flies and emits `state_changed` on landing.
  - `turn_around()` flips `Facing`. A walking pet takes the rest of its stroll the other way, mirrored so it keeps its slope, and stops at a wall that comes first (at once if it is against one: it only turns to face it). Standing, sitting or carried, it only faces the other way.
  - `pet()` is the menu's Pet: a roaming pet stops and keeps still for `PETTING_TIME`, a sitting one stays sitting, and a carried or flying one is left alone.
- **`hearts.py`** and **`heart_window.py`** are the hearts of a stroke. `HeartBurst` (plain Python) is one heart, small or big, or a pair. `HeartWindow` is a small, frameless, always-on-top window, transparent to input, 32×13 art pixels, placed right above the pet's window (at the top of the screen, over the pet, where there is no room); the pets' 32×27 frames stay as they are, since some of them reach row 0 and the hearts would cover them. `PetWindow` ticks the burst in `advance()`, and hides it with the pet. There is no limit on how often it can be stroked (a wait between strokes was tried and removed).
- **`color_change.py`** and **`ring_fade.py`** are how a species with extra palettes (`Species.colorings`) changes color, also plain Python. Both keep a palette index per column of the frame and give it in `columns`, so `PetWindow` treats them alike.
  - `ColorChange` runs a wave of a new coloring from the head (the right edge, as frames face right) to the tail while the pet keeps still, and one back to the usual palette (index 0) when it walks; carried, nothing moves, not even a wave halfway.
  - `RingFade` has the palettes as steps of a fade: 0 is the usual palette, 1 the last. Walking, it fades out; standing, sitting or carried (a thrown pet too), it fades back in. A fade turns back from wherever it got.
  - A species with one palette never changes.
- **`config.py`** holds `Config` and `ConfigStore`, also plain Python. `Config.language` is the interface's language: a code, or None (the default) to follow the system.
  - Writes are atomic: a temp file, then replace.
  - Loading tolerates bad files and fields and falls back to defaults. Settings without a species keep the dog.
  - `Config.facing` (a `Facing`) is saved as "left" or "right", so a turned pet comes back turned. Anything else, or none, faces right.
- **Art pipeline: `sprites.py`, `species.py`, `pets/`, `icon.py`**
  - A frame is a text grid, one character per art pixel ("." is transparent). Every frame of every species shares one 32×27 canvas, so the window never resizes. Frames face right and are mirrored at runtime.
  - `sprites.draw(frame, palette)` paints a frame one image pixel per art pixel. `sprites.draw_columns(frame, palettes, columns)` paints each column in its own palette.
  - Each pet's look, poses, gait, how its art was made and the designs that were approved or turned down are in the docstring of its module in `pets/`. Read it before redrawing a pet, and keep it up to date when the pet changes.
  - The README's pets table has a row per species: its portrait (`docs/pets/<key>.png`, 6 image pixels per art pixel, shown 96 px wide so it stays sharp at 200%), its names in English and Portuguese, how it roams and what it does told to sit. `tests/test_species.py` fails while a picture differs from the art, a species has no row, or a picture has no species, so a new pet needs its row and its picture.
  - `Species` bundles key, label, palette, animations per `Activity`, gait, `locomotion`, `sit_label`, `colorings`, the other palettes it can turn (each defines the same characters as `palette`), `blink`, the steps of its blink, and `color_shift`, how it goes from one palette to another: `ColorShift.WAVES` (`color_change.py`) or `ColorShift.FADE` (`ring_fade.py`). `palettes` is the usual palette followed by the colorings. `image(frame, blinking=, colors=)` renders a frame through a `functools.lru_cache` keyed on the species' identity; `colors` is each column's index into `palettes`, None for the usual one.
  - `Locomotion` says how the pet roams, which is what its WALKING animation shows. Its value is the menu text for roaming again ("Walk", "Fly", "Swim", "Slither", "Hop", "Crawl").
  - `sit_label` is the menu text for sitting down: "Sit" by default, but a species that doesn't sit says what it does instead ("Rest", "Coil up", "Retreat into shell"). Swimmers rest on the bottom: they float in place while STANDING and only touch the ground when SITTING.
  - A blink recolors the eye for a moment. By default (`species.BLINK`) it is one step of 0.15 s that draws "E" pixels in the palette's "B" and "H" pixels in its "N", so every palette must define B and N. A species can blink in steps instead (`Species.blink`, `BlinkStep(look, seconds)`): `blink_step(seconds)` says which step shows that long into a blink, and `image(frame, blink=)` draws it. An empty `blink` (`blink=()`) means the species never blinks: `blink_time` is 0, `blink_step()` is always 0 and `PetWindow` never ticks faster for a blink.
  - `pets/__init__.py` has `ALL_SPECIES` and `species_by_key()`; unknown keys become the dog. A few species have a key that differs from their name in the UI: `parakeet` is the Maritaca, `turtle` the Sea Turtle.
  - `icon.py` draws the app's icon at any size, smooth (antialiased) rather than pixel art: a cream paw, whose shape is the alpha channel of `paw.png`, on a rounded orange tile with a dark rim, in the dog's colors. It is laid out on a grid of 32 units. The margin and the rim are whole pixels, so at 22 px the rim is one sharp pixel, and up to 32 px the paw's edges get extra contrast, which keeps the toes apart. `icon_image(size)` is cached. The README shows it from `docs/icon.png`, drawn at 256 px, and `tests/test_icon.py` fails while that picture differs from what `icon_image(256)` draws.
  - `app_icon()`, the icon of every window and of the tray, holds `SIZES` (the icon theme's usual sizes, 16 to 256 px, which the AppImage installs) and 44 px, the tray's 22 px at 200%.
- **`update_check.py`** asks GitHub's API for the latest release with `urllib` (the AppImage leaves QtNetwork out), and `check_for_update(version)` returns `UpdateAvailable`, `UpToDate`, `DevBuild` (a `+g` build has nothing to compare to) or `CheckFailed`.
  - Settings' "Check for Updates" button runs it whenever it is clicked. `PetController.check_for_update_today()`, called by `main()` after the pet shows, runs it in the background (`BackgroundCheck`, a `QThreadPool` job whose result comes back through a queued signal) the first time the pet starts on a day: `Config.last_update_check` is that day's ISO date, with no setting in the dialogs, on for everybody.
  - Only a new version speaks: `update_message_box()` (shared with the button) opens non-modal with "Get It", the pet's window hidden while it is open, as with Settings. Up to date and dev builds are silent but count as checked; a failed check (offline) is silent and tried again at the next start.
  - `VIRTUAL_PET_NO_UPDATE_CHECK` turns the daily check off; `tests/conftest.py` sets it, so no test or process test reaches GitHub.
- **`wikipedia.py`** and **`article_card.py`** are Ctrl+click on a pet in the adoption and settings dialogs: a popup with its Wikipedia article. `PetButton` (in `dialogs.py`) swallows a Ctrl+left click, so the pet isn't chosen, and emits `info_requested`; a plain click chooses it as before.
  - `TITLES` has an article per species key, in `en` and `pt` (`tests/test_wikipedia.py` fails while a species lacks one). `wiki_language()` takes the interface's language (`i18n.current_language()`) to its Wikipedia, English where there is none.
  - `fetch_article()` reads the REST summary endpoint with `urllib`, as the update check does, with a User-Agent that names the app and its repository, as Wikimedia asks. It then fetches the thumbnail, only from a `*.wikimedia.org` https address, and the card still shows the text if that fails. Disambiguation pages, empty extracts and any failure give None. The link is built from the title, never taken from the answer.
  - `ArticleLoader` runs it in a `QThreadPool` job, one request per species at a time, and remembers articles (not failures) for the dialog's life. `ArticleCard` is a `Qt.Popup` placed under the button, or over it where there is no room, and kept on its screen. It always links to the page and credits Wikipedia's CC BY-SA license.
  - `tests/conftest.py` stubs `wikipedia.fetch_article` for every test, so none reaches Wikipedia.
- **`autostart.py`** is starting with the system, an option of the first run and of Settings (off by default). The system's own entry is the setting, not `Config`: what the desktop's startup list turns off shows as off in Settings.
  - `Autostart` is `is_enabled()`, `enable()` and `disable()`; the last two raise `OSError`, which `app.start_with_system()` and `refresh()` log and never let stop the pet.
  - On Linux, `DesktopEntry` is `~/.config/autostart/virtual-pet.desktop`, written atomically; `Hidden=true` or `X-GNOME-Autostart-enabled=false` in `[Desktop Entry]` means off.
  - On Windows, `RunValue` is `virtual-pet` in `HKCU\...\CurrentVersion\Run`. Startup apps (Task Manager, Settings) turn it off in `Explorer\StartupApproved\Run` (first byte odd), so that counts as off, and `enable()` and `disable()` clear it too. The registry is behind the small `Registry` protocol: tests use a dict, `WindowsRegistry` (winreg, defined only on Windows) is tested under Wine.
  - `launch_command()`: `$APPIMAGE` (the AppImage's own mount is gone once the pet quits) or `sys.executable` when frozen, else `python -m virtual_pet`. As the AppImage and the zip can be moved, `main()` calls `refresh()` after the first run: an entry that is on is written again for the pet as it runs now.
  - `ensure_pet()` and `PetController` take an `Autostart` (the system's by default). `tests/conftest.py` points `XDG_CONFIG_HOME` at a temporary folder for every test, so none touches the user's autostart folder.
- **`pet_window.py`**: `PetWindow` is a frameless, translucent, always-on-top window with `X11BypassWindowManagerHint`.
  - Why unmanaged: Qt always advertises `WM_TAKE_FOCUS`, so KWin activates a managed window when clicked and takes focus from the user's app.
  - `setMask(silhouette)` follows each frame, so clicks around the pet reach the window below.
  - The timer runs at 33 ms while walking, and from a resting tick before a blink to its end if the blink has steps shorter than that tick, 100 ms otherwise. `advance(seconds)` is the public tick that tests drive.
  - A species with colorings gets a `ColorChange`, or a `RingFade` if its `color_shift` is `FADE` (`_color_changer()`), ticked in `advance()` with the pet's activity. Facing left, its columns are reversed, so the waves still start at the head.
  - Click versus drag is decided by `QApplication.startDragDistance()`. While dragging, the allowed area is the screen under the cursor.
  - It only emits `state_changed`, `hide_requested`, `settings_requested` and `quit_requested`; it never persists anything. Hidden, it doesn't roam: `hideEvent` stops its timer.
- **`tray.py`**: `PetTray` is the app's paw print (`app_icon()`) in the system tray, shown only while the pet hides. A click or double click emits `show_requested`, and its menu has "Show <name>" (the default action) and "Quit". Its `QMenu` has no parent, as a tray icon isn't a widget.
  - Qt shows it over D-Bus, as a StatusNotifierItem, where a watcher runs (KDE Plasma, GNOME with the AppIndicator extension), else in the X11 (XEmbed) tray. `QSystemTrayIcon.isSystemTrayAvailable()` says whether there is either; the offscreen platform has neither.
- **`instance.py`**: one pet at a time. `acquire_lock()` is a `QLockFile` in the runtime folder, with `setStaleLockTime(0)`.
  - The lock's holder listens on a Unix socket next to it (`virtual-pet.socket`, mode 0600), watched by a `QSocketNotifier`. A connection is a request to show the pet: nothing is read. The next lock holder replaces a socket left by a crash.
  - A second start, which can't get the lock, connects (`ask_to_show()`), logs "already running: it was asked to show the pet" and exits 0. If nothing answers, it logs "already running" and exits 1.
  - Windows' Python has no Unix sockets, so there (`WINDOWS`) the requests go through a named pipe, Qt's `QLocalServer`/`QLocalSocket` with `UserAccessOption`, named after the socket's path (`pipe_name()`). QtNetwork is imported only there: the AppImage leaves it out, as on Linux it links Kerberos and more.
  - On Windows Qt's runtime folder is the user's home, so the lock goes in the temp folder (`%LOCALAPPDATA%\Temp`). The settings land in `%LOCALAPPDATA%\virtual-pet\config.json` with no change.
- **`i18n.py`** shows the interface in English, the language of the texts in the code, or in a translation.
  - Translations are Qt Linguist files in `src/virtual_pet/translations/`: `virtual_pet_<code>.ts`, edited in Qt Linguist, and the `.qm` that `pyside6-lrelease` compiles from it and the app loads. Both are committed. `LANGUAGES` maps each code to the language's name in itself.
  - `use_language(code)` replaces the installed translators: the app's `.qm` and Qt's own `qtbase_<code>.qm`, which translates Qt's texts (the Cancel button, a text field's context menu). None follows the system (`QLocale.system().uiLanguages()`, the closest language, else English). A file that fails to load is logged as "Could not load".
  - It also sets the app's display name, `APP_DISPLAY_NAME` ("Virtual Pet", "Pet Virtual" in Portuguese). On X11 Qt ends every window title with it, and an untitled window, like the pet's, gets just the name. `APP_NAME` in `app.py` ("virtual-pet") names the settings folder, the lock and the X11 window class, and is never translated.
  - Texts with values in them use Qt's markers, `%1`, `%2`…, which `arg(text, *values)` fills in all at once (so a pet named "100%2" stays as it is). Qt Linguist warns when a translation drops a marker, and so does `tests/test_i18n.py`.
  - Texts are marked with `self.tr()` in a class, `QCoreApplication.translate(context, text)` elsewhere, or `QT_TRANSLATE_NOOP(context, text)` where a module-level value is defined (the one in `i18n.py`, typed `str`; PySide6's returns `object`, and lupdate goes by the name): species labels ("Species" context), the menu's roam and sit texts ("PetWindow") and the app's name ("App"). Those are translated where they are shown. PySide6's `self.tr()` uses the class it is written in as the context, as lupdate does, even when a subclass calls it.
- **`dialogs.py`**: `PetDialog` is the adoption dialog on first run, with a "Show the pet when the system starts" check box under the name. `SettingsDialog` is the same plus a Language field ("System default", then each language by its own name), inserted above the check box, and the version. `ask_for_new_pet()` returns an `Adoption(pet, starts_with_system)`; `ask_for_changes()` takes and returns `Preferences(pet, language, starts_with_system)`.
  - The pets are a grid of checkable buttons, `PETS_PER_ROW` per row. Every button gets the size of the largest one: in a `QGridLayout`, fixed-width buttons of different widths squeeze their column to the narrowest and cut the longer names.
  - The buttons are children of the dialog from the start, so its style sheet's padding counts when they are measured.
  - The layout's `SetFixedSize` makes the dialog exactly as large as its contents, so it can't be resized or maximized. Qt opens a window at most 2/3 as wide as the screen, and without that (or with an explicit minimum width, which turns the layout's minimum off) the cards overlapped with the longer Portuguese names on the 800-pixel test screen.
- **`app.py`**
  - On Linux Wayland sessions it sets `QT_QPA_PLATFORM=xcb` (when XWayland is available and no non-Wayland platform was chosen), because Wayland forbids self-positioning and always-on-top.
  - It sets `GDK_GL=disable` unless the user set it. On GNOME-like desktops Qt draws its dialogs with the GTK theme, and GTK would otherwise start OpenGL and load the system's GPU driver (Mesa and LLVM, about 50 MB) that the pet never uses.
  - `main()` takes the lock (`instance.py`) and listens for later starts at once, even during the first run's dialog (whose requests are dropped), so a later start always gets an answer. A `finally` closes the socket.
  - SIGINT/SIGTERM trigger `QTimer.singleShot(0, QApplication.exit)`, because Qt 6's `quit()` does nothing outside `app.exec()`, for example during the first-run dialog. A heartbeat timer lets the Python signal handlers run.
  - `main()` applies the saved language before `ensure_pet()` shows the adoption dialog on first run. The controller applies a language chosen in Settings at once: the menu and the dialogs are built each time they open. The language is never applied outside `main()` and the Settings, so the tests don't follow the machine's language.
  - `PetController.hide_pet()` hides the window and, where there is a system tray, shows the tray icon; it asks at each hide, as a tray can come and go. Without a tray nothing shows (the user asked for no message): opening the app again brings the pet back. `show_pet()`, from the tray or a later start, undoes the hiding. Hiding isn't saved: each start shows the pet. The controller takes `tray_available`, so tests choose whether there is a tray.
  - `PetController` wires the window signals to `dialogs.ask_for_changes()`. It saves to `~/.config/virtual-pet/config.json` (`GenericConfigLocation`, respects `$XDG_CONFIG_HOME`) after every user interaction and on quit.
- **`appimage/`** builds the AppImage on the developer's machine.
  - `virtual-pet.spec` (PyInstaller) keeps the xcb, wayland and offscreen platforms and the platform themes (GTK 3, XDG portal). It drops the other Qt plugins (embedded displays, VNC, networking, input devices, image formats other than SVG and JPEG, which is what Wikipedia's pictures are), PySide6's QtNetwork and QtDBus modules (QtGui's own D-Bus code, which puts the tray icon on KDE's panel, links `libQt6DBus`, which stays, with `libdbus-1`), and Qt's translations except `qtbase_<code>.qm` for each language the pet has a `.qm` for. It bundles the app's `.qm` files and `paw.png` as data. The license check doesn't look at data files: the app's are GPL, and Qt's are covered by the Qt notice.
  - The spec also leaves out the libraries in the AppImage project's excludelist (glibc, libstdc++, GL, core X11/xcb, fontconfig, freetype, harfbuzz, zlib…), then every library that no extension module, plugin or libpython still links to. It stops if the machine lacks a library that isn't in that list, and writes `bundled-files.json` with the source of every bundled binary and module.
  - `build.py` first starts itself again in `build/appimage/venv`, through `UV_PROJECT_ENVIRONMENT` and `uv run --managed-python --locked --group build`. So the bundle always embeds uv's python-build-standalone Python, whatever the dev `.venv` runs on. Homebrew's Python, for example, isn't portable and has no package licenses.
  - The AppImage is named after `pyproject.toml`'s version only when built from a clean checkout of the release tag, `v<version>`. Any other build adds `+g<commit>` (and `.dirty` for uncommitted changes to tracked files; untracked files don't count), and a release tag on the commit that isn't that version stops the build. `pack()` passes the version to appimagetool as `$VERSION`, which it writes into the AppDir's menu entry as `X-AppImage-Version`.
  - `build.py` then runs PyInstaller and lays out the AppDir: `AppRun` (`exec`, so signals reach the pet), the `.desktop` file (its name, description and keywords also in Portuguese), the icons and the licenses. It packs the AppDir with appimagetool and the type2 runtime, pinned by URL and SHA-256 and cached in `build/appimage/tools/`. Then it runs `pytest -m process` against the AppImage and prints the glibc version the AppImage needs.
  - Licenses: every bundled file must be covered by a notice or a system package, or the build stops.
    - `DISTRIBUTION_NOTICES` maps Python distributions to notices; a new dependency that lands in the bundle needs an entry.
    - System libraries get their package's license files (dpkg, rpm or pacman). dpkg and pacman get one query for all the files: `dpkg-query --search` reads every package's file list on each call, so a query per file takes minutes on a desktop. Package queries, `ldd` in the spec and downloads have timeouts, so nothing hangs silently.
    - uv's Python (python-build-standalone) gets the texts from the matching full build, checked against the release's SHA256SUMS.
    - `appimage/licenses/` holds the texts no package provides: LGPL-3.0 for Qt for Python, and ICU 73.2's license. The build stops if the bundled ICU's major version changes.
- **`.github/workflows/release.yml`** runs on a pushed `v*` tag, or by hand on any branch (`workflow_dispatch`).
  - `checks` (ruff, ty, pytest) gates two builds: `linux` runs `appimage/build.py` on `ubuntu-22.04`, so the AppImage needs only glibc 2.35, with `fuse3` for its process tests; `windows` runs `windows/build.py` on `ubuntu-24.04` with WineHQ's `winehq-stable`, pinned to the 11.0 the build is tried with locally.
  - `QT_PACKAGES` lists the system libraries Qt for Python needs there; a library the AppImage's spec finds missing goes in it.
  - Only on a tag, `release` creates a draft release with both files (`--generate-notes`, a prerelease for an `a`/`b`/`rc` tag), or replaces them in an existing one. Publishing it stays by hand. A run by hand keeps the files as artifacts, named after their commit.
  - Actions are pinned by commit SHA, with the version in a comment.
- **`windows/`** builds the Windows zip on the Linux machine, as PyInstaller doesn't cross-compile. The user has no Windows machine of their own: Wine is the build's only test, and it can't show how the window behaves on Windows.
  - `build.py` loads `appimage/build.py` as a module (`common`) for the version naming, the downloads and `full_build_licenses()`. It runs in the dev `.venv` (it needs Qt only to draw the icon).
  - Windows' Python is python-build-standalone's `install_only` build, pinned by `PYTHON_VERSION` and `PYTHON_RELEASE` and checked against the release's SHA256SUMS. `uv export` plus `uv pip install --target --python-platform x86_64-pc-windows-msvc` put the Windows wheels of `uv.lock` in `build/windows/site-packages`, which PyInstaller, run by `wine python.exe`, finds through `PYTHONPATH`.
  - Wine commands get the build's own prefix (`build/windows/wine`), no `DISPLAY` or `WAYLAND_DISPLAY`, and `WINEDLLOVERRIDES` turning off Mono, Gecko and `winemenubuilder.exe`. Without that last one, `wineboot` rewrote the user's Wine file associations and icons in `~/.local/share`.
  - Qt 6.11's Core imports 20 `ucnv_*` functions from Windows' own `icuuc.dll` (Windows 10 1903+), which Wine lacks. `stub_dll()` writes a DLL exporting them all as `xor eax, eax; ret` into the prefix's system32; the names come from Qt6Core.dll's imports, read with the Windows packages' pure-Python pefile. The stub never goes in the bundle.
  - `virtual-pet.spec` keeps the Windows, offscreen and style plugins and the JPEG image format (Wikipedia's pictures; PNG is built into Qt), then only the DLLs linked from what is left, so OpenGL and most of the C++ runtime go. The exe is `VirtualPet.exe`, windowed, with the icon (`write_icon()`, PNGs in an .ico) and a version resource (`write_version_info()`).
  - Licenses: the bundle's `licenses/` gets the pet's GPL, Qt's LGPL, python-build-standalone's texts, PyInstaller's COPYING and `THIRD-PARTY-NOTICES.txt` (CRLF). The Visual C++ runtime DLLs have a notice without texts, as a GPL system library. A file from the Wine prefix (a Wine DLL) stops the build.
  - The smoke test starts the bundle offscreen under Wine with a Portuguese config in the prefix's profile, waits for the lock, starts it again (exit 0, "asked to show") and fails on "Could not load" or a traceback. Then `wineserver --kill`: no graceful quit is tested. With `DISPLAY` set, the bundle also runs on the real desktop through Wine's X11 driver.
  - Scaling that isn't whole (125%, 150%, common on Windows) draws uneven art pixels; it is known and documented, not fixed.

## Invariants and conventions

- Only one pet is ever on screen: one window in one app instance. Changing the species in Settings swaps the pet in the same window and spot.
- `tests/test_species.py` enforces the art invariants for every species:
  - all frames are 32×27;
  - they use only palette characters;
  - the lowest visible row is 25 for sitting, for standing unless the species swims, and for walking only if the species walks, slithers, crawls or hops;
  - every frame contains the E and H eye pixels.
- Identifiers, file names, comments and docs are in English. UI texts are written in English in the code and translated in `src/virtual_pet/translations/` (Brazilian Portuguese so far). The user writes in Portuguese.
- Commits follow Conventional Commits (`type(scope): summary`) in English, with a short body and a `Co-Authored-By` trailer for the Claude model that made the change.
- The version is static in `pyproject.toml`, as the `modern-python` skill advises, not derived from git. A release is the `uv version --bump` commit, `chore(release): X.Y.Z`, with an annotated tag `vX.Y.Z` on it; the README's Releasing section has the commands.
- New or changed pet art, and the app icon, must be shown to the user as images first: enlarged poses, plus real size on dark and light backgrounds. Wait for approval before it touches the code. The `draw-pet` skill (`.claude/skills/draw-pet/`) holds the process and the rules for drawing or redrawing a pet. The icon the user chose is the smooth cream paw on the rounded orange tile; it replaced a 32×32 pixel-art paw, and pixel-art versions of the new paw were turned down.
- The AppImage is x86-64 Linux only. After changes to the window, the tray or the Windows build, the zip needs trying on a Windows PC again, which the user does.
- The project is GPL-3.0-only: the full text is in `LICENSE`, the copyright notice in the README's License section, and `pyproject.toml` declares it. Code or art copied into the program needs a GPL-3.0-compatible license, and every third-party file keeps its license text next to it.
- Agent skills are project-scoped in `.claude/skills/` and pinned in `skills-lock.json`, except `draw-pet`, the project's own: it has no upstream to pin, and the project's license covers it. Ruff checks its script, and `pyproject.toml` relaxes a few rules for skill scripts, as for the build scripts.
  - Install only trusted skills, and never with `-g`: `npx skills add <owner/repo> --skill <name> -a claude-code -y --copy`.
  - A personal skill in `~/.claude/skills` with the same name overrides the project one.
  - Each skill's folder carries its upstream license. `npx skills` copies only the skill's folder and wipes it on every reinstall or update. The `LICENSE` files of `tdd` and `modern-python` come from the root of their repos, so restore them with `git restore` after an update.

## Testing and live checks

- `tests/conftest.py` forces Qt's offscreen platform, a single 800×800 virtual screen. The "This plugin does not support setting window masks" messages it prints are expected. `filterwarnings = "error"` is on. It puts the interface back in English after every test.
- `tests/test_i18n.py` runs `pyside6-lupdate` and `pyside6-lrelease` from the venv. It fails while a text in the code is untranslated (lupdate marks it "unfinished") or a translation's text is gone from the code ("vanished"), and while a `.qm` differs from what its `.ts` compiles to.
- `tests/test_instance.py` runs each test as on Linux (a Unix socket) and as on Windows (a named pipe, which works on Linux too) by setting `instance.WINDOWS`; the socket-only ones skip where Python has no Unix sockets. It checks the lock and the socket in `tmp_path`. `tests/test_windows_build.py` checks the ICU stub's exports, the .ico, the version resource and the Wine paths without Wine.
- The whole suite, but the process tests, also runs under Wine on Windows' Python: with the Windows wheels in a `--target` folder (all groups) and `PYTHONPATH="<site-packages>;<src>"`, `wine python.exe -m pytest --no-cov -p no:cacheprovider -m "not process" --ignore=tests/test_i18n.py --ignore=tests/test_build.py`, in the build's prefix (it needs the ICU stub).
- `tests/test_tray.py` and the controller's tests say whether there is a tray (`tray_available`): the offscreen platform has none.
- `tests/test_build.py` loads `appimage/build.py` as a script (not a module of the package) and checks how it names the version, partly in a throwaway git repository shielded from the user's git settings (`GIT_CONFIG_GLOBAL`, `GIT_*` variables).
- `tests/test_app.py` also starts the real app in subprocesses, with temporary `XDG_CONFIG_HOME` and `XDG_RUNTIME_DIR`. It waits for the lock and the socket to exist before sending signals or starting the app again. Those tests are marked `process`, and `VIRTUAL_PET_EXECUTABLE` makes them start a built app (the AppImage) instead of `python -m virtual_pet`. One starts the app in Portuguese and fails on "Could not load", so a bundle missing a `.qm` is caught.
- Trying the app on the real desktop:
  - Set those same two variables to temporary dirs, so the user's settings and lock stay untouched.
  - `xwininfo` and `xprop` inspect the window through XWayland: expect `Override Redirect State: yes` and an unchanged `_NET_ACTIVE_WINDOW`.
  - While the pet hides, `busctl --user get-property org.kde.StatusNotifierWatcher /StatusNotifierWatcher org.kde.StatusNotifierWatcher RegisteredStatusNotifierItems` lists its tray icon among the others.
  - Take screenshots with `spectacle -b -n -f -o file.png`, without `QT_QPA_PLATFORM=offscreen` in its environment, and crop them to the pet's area.
